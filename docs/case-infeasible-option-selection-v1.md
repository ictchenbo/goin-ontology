# 决策方案可选性与评分时效修复 v1

[截图依据] 案例的“选定方案”下拉框包含未通过硬约束的“申请法定措施”，点击“记录决策”后才显示拒绝原因；同一区域还展示了此前记录的另一项决策。

## 目标与流程

1. [设计方案] 决策区沿用评分结果判定可选性。不可行或未参与当前评分的方案仍可查看，但在选择框中禁用，并直接展示不可行原因；默认选中当前评分中最高的可行方案。
2. [设计方案] 新快照或新方案形成后，旧评分不再允许记录决策。页面引导用户回到“方案与评估”重新评分；服务端做同样的校验。
3. [设计方案] 决策记录保留为历史信息。提交审批只接受基于当前评分、且与选择框一致的决策记录；旧记录不得因下拉框选中相同方案而自动恢复效力。
4. [设计方案] 硬约束不因人工覆写而放宽。人工覆写只表示选择了非最高分的**可行**方案。

## 数据接口

[设计方案] 不修改 SQLite 表结构。新评分在 `score_run.facts_json` 中记录 `snapshotId`；旧评分通过快照和评分时间判断是否适用于当前快照。案例详情返回 `scoreRun.current` 和决策记录的 `scoreRunId`，用于页面提示。新增方案晚于评分时，旧评分同样失效。

## 验收

- [验收目标] 现有案例中的“申请法定措施”显示为不可选，并可看到未核实事件和法定授权两项原因。
- [验收目标] 新快照或新方案之后，页面先要求重新评分，直接调用记录决策或提交审批接口也会被拒绝。
- [验收目标] 重新评分后，可行方案可记录决策；旧评分绑定的决策不能直接提交审批。
