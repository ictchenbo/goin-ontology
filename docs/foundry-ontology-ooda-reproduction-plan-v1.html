以 Ontology 为核心的 Foundry 产品复现方案

[文档依据]基于 Palantir 官方产品文档分析 v1 所梳理的“数据、逻辑、行动”体系，以及 Ontology 的对象、链接、Action、Function 与 Scenario 机制。

[方案设计]以可执行的业务语义模型承载 Observe → Orient → Decide → Act，形成可回溯、可推演、可审批、可执行、可反馈的决策闭环。

单机 / 小团队部署Node.js + TypeScript + ReactSQLite前端 18000 · 后端 3000大规模处理与高性能优化暂不纳入

01 · 目标与范围

[方案设计]复现目标是“能够围绕业务对象完成复杂决策”，而不是照搬 Foundry 的全部基础设施与页面。最小闭环必须让用户从事实进入，形成情境，比较方案，授权执行，并用结果修正下一轮判断。

Ontology
[方案设计] 唯一业务语义层

[方案设计]类型、属性、链接、规则、动作、权限与证据围绕同一组对象组织；所有应用视图通过它查询与写回。

OODA
[方案设计] 产品主流程

[方案设计]观察数据、形成情境、比较备选、执行动作四阶段均产生有版本的记录；结果重新进入观察阶段。

Decision Case
[方案设计] 决策工作单元

[方案设计]每个案例冻结事实、模型和规则版本，保存备选方案、约束、评分、审批、执行与结果。

[范围边界]首版聚焦单实例、有限数据量、人工主导的业务决策。分布式计算、海量实时流处理、复杂 MLOps、完整通用低代码平台和 Palantir 专有服务兼容性均不作为交付目标。

[方案设计]交付时保留通用 Ontology 建模能力，并用一个跨实体、跨约束的供应链异常处置案例验证其表达力；业务案例是验收样板，不写死在平台内核。

模型定义层

  • [方案设计]类型标识与语义版本分离；已发布类型不可原地破坏性修改，变更需迁移。
  • [方案设计]属性支持字符串、数值、布尔、日期时间、枚举、引用、JSON 结构；数值可声明单位与上下界。
  • [方案设计]关系声明起点、终点、方向、1:1 / 1:N / N:M 基数、唯一性与可选生命周期。
  • [方案设计]Interface 定义跨类型的共同属性和可执行能力，供统一查询与工作台模板使用。

实例与证据层

  • [方案设计]对象实例采用稳定 ID；每次写入增加修订号，并保留修改前后值、作者和原因。
  • [方案设计]事实记录来源、采集时间、业务生效时间、可信级别与原始记录标识。
  • [方案设计]链接既可由导入建立，也可由 Action 维护；删除默认采取失效标记以保留历史。
  • [方案设计]对象详情合并当前状态、关联对象、证据、历史动作和计算指标。
[方案设计]核心约束：业务写入只经过 Action Engine；导入通过受控 Ingestion Action 提交。这个统一入口让校验、权限、审计和事件生成有稳定位置。

模型版本与变更

草稿→校验→影响分析→发布→实例迁移→归档旧版

[方案设计]新增可选属性可直接发布；必填属性、枚举缩减、关系基数变化和删除字段必须提供迁移规则并经过试运行。决策案例继续引用创建时的模型版本，以保证历史解释一致。

04 · OODA 全链路产品流程

O / OBSERVE

观察事实

[方案设计]CSV、JSON、Webhook 与人工表单进入来源区；字段映射和实体匹配生成对象或事件，保留来源与时间信息。

[方案设计]质量检查覆盖必填、类型、重复、外键、数据新鲜度；异常进入待处理队列。

产物：事实快照 + 异常事件

O / ORIENT

构建情境

[方案设计]围绕触发对象提取指定深度的关系邻域、指标、规则结论、冲突事实与未确定假设。

[方案设计]为 Decision Case 冻结对象修订、模型版本、规则版本和证据引用。

产物：Situation Snapshot

D / DECIDE

比较备选

[方案设计]生成或手工录入多个 Alternative；先执行硬约束，再运行推演与加权评分，显示差异、风险和证据。

[方案设计]决策者记录选择理由、反对意见及审批结果；不可行方案仍保留原因。

产物：Decision Record

A / ACT

执行与反馈

[方案设计]Action Engine 重检前置条件与权限，事务性写回 Ontology；外部副作用经 Outbox 可靠提交。

[方案设计]跟踪执行状态和结果指标，与预测比较后触发下一轮 Observe。

产物：Action Run + Outcome

[文档依据]Foundry 平台概览以数据、逻辑和行动组织决策；Action 使变更进入 Ontology，Scenario 用于推演后果；Automate 可根据条件执行效果。平台概览 · Scenario · Automate

[方案设计]状态机：New → Observed → Oriented → OptionsReady → PendingApproval → Approved → Executing → Completed / Failed → OutcomeReviewed → Closed；取消与退回作为显式转换保存原因。每次转换由角色和前置条件约束。

05 · 支撑复杂业务决策的元模型

[方案设计]“复杂”在这里指多对象、多目标、硬约束、跨步骤影响和多人审批可以在同一案例内表达，并能追溯到输入事实和规则版本。

概念关键字段或语义为什么需要
Decision Type[方案设计]触发条件、目标对象、角色、所需事实、策略版本、审批路线。[方案设计]让同类决策可重复执行和演进。
Goal / Criterion[方案设计]指标方向、单位、目标、权重、阈值、解释模板。[方案设计]表达成本、时效、风险、服务水平等冲突目标。
Constraint[方案设计]硬/软分类、适用范围、表达式、失败消息与依据。[方案设计]先排除不可执行方案，再比较优劣。
Rule / Derived Metric[方案设计]输入依赖、确定性表达式、输出类型、版本与测试样例。[方案设计]使情境判断与评分可复算。
Alternative / Scenario[方案设计]拟议 Action 序列、对象覆盖值、假设、推演结果、差异。[方案设计]在不改变真实状态时探索“如果这样做”。
Evidence / Assumption[方案设计]来源对象、文件、记录、时间、可信度、有效期与责任人。[方案设计]区分已观察事实与待验证判断。
Decision Record[方案设计]候选集、不可行原因、评分、所选方案、解释、异议、审批。[方案设计]支持审计、复盘与知识积累。
Outcome[方案设计]预期值、实际值、采集时点、偏差、归因与复盘结论。[方案设计]完成反馈环，并识别规则失效。

约束与评分的执行顺序

  1. [方案设计]验证事实完整性和新鲜度；缺失关键输入时标记“无法判断”。
  2. [方案设计]检查权限、资源容量、预算、时窗、法律/业务红线等硬约束。
  3. [方案设计]对可行方案运行级联计算，得到成本、交期、风险等预测。
  4. [方案设计]按版本化权重和归一化规则计算分数，同时展示单项值，允许人工覆议并记原因。

规则表达方式

[方案设计]首版使用可视化规则编辑器与受限 DSL：比较、布尔组合、聚合、对象关系查询、时间区间和简单算术。表达式必须能枚举依赖字段与读取范围。

[方案设计]高级算法通过受控“计算器”插件接口接入，输入输出采用明确 Schema、超时和版本约束；插件不得直接写 Ontology。

[范围边界]首版不承诺通用优化求解器、任意脚本执行或自动学习权重。

06 · 验证案例：供应链异常处置

[方案设计]案例从“某供应商发货延迟”开始，决策者要在订单交期、转运成本、替代供应风险和仓库容量之间选择措施。该案例验证跨实体关系、硬约束、方案推演、审批和结果反馈。

对象与关系

[方案设计]对象类型：Supplier、Facility、InventoryLot、PurchaseOrder、SalesOrder、Shipment、CapacityWindow、Disruption、DecisionCase、ActionPlan、Outcome。

[方案设计]关键关系：供应商供货、库存位于仓库、销售订单需求物料、货运履行采购订单、异常影响货运、备选措施使用库存/产能窗口、结果关联决策案例。

事实、方案和执行

[方案设计]事实包括预计到货时间、可用库存、客户交期、替代供应商资格、转运能力及预算；不确定输入单列为 Assumption。

[方案设计]备选方案示例：跨仓调拨、加急运输、替代采购、维持原计划。每项方案含拟议 Action、成本与交期预测。

可交互的决策评分演示

[示例假设]下列分数是为解释多目标比较而设的虚构输入，量纲均归一到 0–100；其中“替代采购”因供应商资格约束未满足而不可选。拖动权重仅改变可行方案排序，不会修改任何真实数据。

[方案设计]正式系统除了总分，还必须显示每项指标、权重版本、事实来源、约束结果与情境差异，并允许决策者解释为何选择非最高分方案。

[方案设计]示例失败路径：若执行前发现仓库可用量已变，Action 前置条件会因对象修订冲突而拒绝；案例返回“待重新定向”，刷新事实后再次推演，而不是沿用过期评分。

07 · 单机优先的技术架构

[方案设计]采用 Node.js 全栈式架构；前端 TypeScript + React、Tailwind CSS、shadcn/ui（复制组件代码）、Radix UI 与 Lucide React；后端 TypeScript；SQLite 存储。前端默认端口 18000，后端默认端口 3000，支持暗色模式、移动端布局和 WAI-ARIA 语义。

服务模块边界

  • [方案设计]Ontology Registry：类型、属性、链接、Interface、模型版本与迁移。
  • [方案设计]Object Store：对象、关系、历史、查询、局部图和证据。
  • [方案设计]Situation Engine：事实快照、规则计算、冲突及新鲜度。
  • [方案设计]Decision Engine：备选、约束、评分、解释与审批。
  • [方案设计]Scenario Engine：隔离覆盖、依赖重算、差异与结果比较。
  • [方案设计]Action Engine：权限、前置条件、事务、事件和外部副作用。

SQLite 设计原则

  • [方案设计]类型定义、对象索引、链接、案例、事件采用规范化表；可变业务属性放在带 Schema 校验的 JSON 字段中。
  • [方案设计]为 type_id、object_id、case_id、status、event_time 和常用关联字段建立索引；针对频繁筛选的业务属性增加投影列。
  • [方案设计]开启外键与 WAL；每次 Action 在单个数据库事务中提交对象变更、案例状态、审计事件和 Outbox 记录。
  • [方案设计]大文件保存在受控文件目录，数据库仅保存路径、哈希和访问标签。
  • [范围边界]首版以单服务进程、单数据库写入为运行假设；不设计分布式一致性。
[方案设计]部署交付包含 Linux 的 start.sh 与 stop.sh 一键脚本；脚本负责依赖检查、数据库迁移、服务启动、PID 管理和健康检查。当前文件是方案文档，尚未实现这些脚本。

09 · 权限、执行可靠性与 AI 边界

权限与数据标签

[文档依据]官方文档区分可随数据衍生传播的强制控制与仅在读取时过滤的行列权限；后者不会自动保护 Function 输出、模型输出或 Action 写入。权限传播 ↗

[方案设计]首版采用用户/角色授权、对象及字段读取策略、Action 执行策略、数据标签；任何衍生值与导出结果的标签取输入标签并集，降级须经显式授权。

[方案设计]Case Snapshot、Alternative、AI 提示与结果均记录来源标签；服务端统一做读取裁剪与输出标签检查。

Action 可靠执行

[方案设计]Action 定义参数 Schema、执行角色、前置条件、目标对象、写入集合、审批策略、外部副作用与补偿说明。

[方案设计]执行时按“授权 → 新鲜度/修订校验 → 硬约束 → 原子写入 → 审计及 Outbox”顺序处理；同一幂等键重复请求只产生一次业务效果。

[方案设计]外部副作用按至少一次发送语义设计，要求目标系统或适配器具备幂等处理；失败提供重试、人工处理及补偿记录。

审批与职责分离

[方案设计]审批策略可按 Action 类型、金额、风险分数和影响对象配置；提案人、审批人与执行人角色可分离。

[方案设计]审批通过后如果关键事实或对象修订发生变化，批准自动失效并要求重算；所有覆议必须留理由。

[文档依据]官方 Automate 文档建议在规划自动化时记录目的、范围、执行身份与影响，并决定何时进行人工复核。Automate ↗

AI 作为受控建议器

[方案设计]可选 AI 适配器只返回候选解释、缺失事实提示或备选方案草案；所有输出标注“建议”、引用输入证据，并通过同一约束与审批流程。

[方案设计]AI 评估集覆盖事实幻觉、约束遗漏、证据引用错误与方案质量；记录模型版本、提示模板版本、输入标签和人工纠正。

[范围边界]核心功能不依赖外部 LLM；不允许 AI 直接绕过 Action Engine 写入。

[方案设计]按可运行的纵向切片推进，每一阶段都形成可演示成果和回归验证。下一阶段以上一阶段的模型与契约为基础。

阶段交付内容完成条件
0 · 决策样板[方案设计]供应链案例对象图、决策类型、约束清单、四种备选、角色矩阵和合成样例数据。[验收目标]业务专家能逐项确认输入、动作、结果和不可行条件。
1 · Ontology 内核[方案设计]Schema Registry、对象/链接存储、版本、导入、查询、审计和基础权限。[验收目标]可配置样板模型并导入数据；对象页能显示关系、来源和历史。
2 · OODA 工作台[方案设计]Case Snapshot、情境规则、备选、约束、评分、审批和决策记录。[验收目标]一个异常可形成完整案例，至少比较三种备选并解释排除原因。
3 · Scenario 与 Action[方案设计]隔离推演、差异查看、事务写回、版本冲突、Outbox、结果反馈。[验收目标]推演不污染正式对象；批准后写回一次；失败有可追溯的恢复状态。

[方案设计]交付优先级：Ontology 内核与 Action 一致性高于外观复刻；完整人工决策闭环高于 AI 功能数量；第二个领域样板用于检验平台通用性。

11 · 产品验收与明确的非目标

功能验收

  • [验收目标]无需改代码即可建立样板所需的对象类型、属性、关系、接口、Action 和 Decision Type。
  • [验收目标]同一案例能使用多个相关对象、至少三项硬约束、三项评分指标和三种备选方案。
  • [验收目标]可回放任一已完成案例所用的事实快照、模型/规则版本、评分、审批、执行及结果。
  • [验收目标]Scenario 覆盖值不会修改正式对象；最终 Action 执行时重检权限和前置条件。
  • [验收目标]对象修订冲突、审批失效、外部执行失败、重复请求和缺失关键事实均有明确状态与恢复路径。

质量验收

  • [验收目标]权限测试覆盖对象读取、字段裁剪、Action 执行、Case 导出和衍生值标签。
  • [验收目标]重要路径有端到端测试：导入 → 定向 → 比选 → 审批 → 执行 → 结果。
  • [验收目标]前端支持暗色模式、移动端核心流程、键盘操作和可访问的表单错误提示。
  • [验收目标]提供数据库迁移、备份/恢复说明、Linux 启停脚本和基础健康检查。
  • [验收目标]第二个业务领域样板复用相同引擎，只新增模型、规则、表单配置和样例数据。
[范围边界]不验收分布式 ETL、超大数据集扫描、毫秒级实时控制、通用机器学习训练平台、全量 Foundry API 兼容、完整 Palantir 权限语义、复杂流程编排器和无监督自动执行。

[方案设计]首版产品成功标准是“复杂决策能被建模、解释、执行并复盘”，而非吞吐量或 UI 与 Foundry 的像素级一致。
